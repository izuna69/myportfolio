# 🚀 포트폴리오 풀스택 웹 애플리케이션 기술 스택 및 발표 심층 방어(Q&A) 가이드

이 문서는 본 포트폴리오 프로젝트의 **풀스택(Frontend & Backend) 아키텍처, 기술 스택 선정 이유(도입 배경)** 및 프로젝트 발표·평가·기술 면접 시 나올 수 있는 **모든 기술적 질문에 완벽하게 대답할 수 있는 심층 방어 가이드**입니다.

## 🏗️ 1. 프로젝트 개요 및 전체 아키텍처

본 프로젝트는 단순한 정적 웹사이트를 넘어, **관리자가 웹상에서 실시간으로 포트폴리오 데이터를 조회·생성·수정·삭제(CRUD)하고 고용량 이미지를 동적으로 관리할 수 있는 맞춤형 풀스택 CMS(Content Management System) 포트폴리오**입니다.

```
       [ Frontend (Vite + React 19 + TypeScript) ]
                          ▲
                          │  REST API (JSON / FormData)
                          ▼
        [ Backend (Spring Boot 4 / Java 17) ]
            ▲                           ▲
            │                           │
  [ PostgreSQL Database ]       [ Local File System ]
  (프로젝트 메타데이터 & 글)    (썸네일 등 이미지 물리 저장)
```

| 구분 | 주요 기술 스택 | 적용 부문 |
| :--- | :--- | :--- |
| **Frontend** | React 19, TypeScript, Vite | 사용자 인터페이스 및 컴포넌트 생태계 |
| **Styling & UX** | Tailwind CSS, Framer Motion | 디자인 시스템, 반응형 웹, 마이크로 애니메이션 |
| **Data & Chart** | Axios, Apache ECharts (`echarts-for-react`) | REST API 통신, 개발자 역량/스킬 시각화 |
| **Backend** | Java 17, Spring Boot 4.1 | 비즈니스 로직, REST API Controller, DTO Validation |
| **Data & ORM** | Spring Data JPA (Hibernate), PostgreSQL | 객체-관계 매핑(ORM), 데이터베이스 영속성 처리 |
| **File Server** | Spring Multipart, Local File System (`LocalFileUploader`) | 고스트/누수 이미지 파일 동기화 삭제 및 관리 |

## 🛠️ 2. 프론트엔드(Frontend) 기술 스택 및 도입 배경

### 1) React 19 & TypeScript
*   **도입 배경 및 이유**:
    *   **선언적 UI와 재사용성**: 프로젝트 카드, 프로필 사이드바, 다국어 모달 등 반복되고 상호 작용이 깊은 UI 요소를 모듈화된 컴포넌트로 구축하기 위해 채택했습니다.
    *   **TypeScript 기반 강력한 타입 안정성**: 프론트엔드와 백엔드 간 API 통신(`ProjectRequestDto` 등) 시 발생할 수 있는 런타임 타입 에러(Null Reference, 오타 등)를 컴파일 시점에 완벽히 원천 차단하여 개발 안정성과 생산성을 극대화했습니다.

### 2) Vite (빌드 도구)
*   **도입 배경 및 이유 (Webpack / CRA 대비 장점)**:
    *   기존 Create React App(CRA)의 Webpack은 프로젝트 수정 시마다 전체 모듈을 번들링하여 개발 서버 가동 및 HMR(Hot Module Replacement) 속도가 느리다는 고질적 한계가 있습니다.
    *   **Vite**는 Go 기반의 **esbuild**를 사용하여 10~100배 빠른 프리 번들링을 제공하며, 브라우저의 네이티브 ES Module(ESM)을 활용해 코드를 온디맨드(On-demand)로 전송하므로 수정 즉시 반영되는 최고 수준의 DX(개발자 경험)를 제공합니다.

### 3) Tailwind CSS (유틸리티 퍼스트 스타일링)
*   **도입 배경 및 이유 (Styled-Components / CSS-in-JS 대비 장점)**:
    *   **번들 및 런타임 퍼포먼스**: CSS-in-JS는 런타임에 스타일을 파싱하고 인젝션하므로 브라우저 런타임 비용이 들지만, Tailwind는 빌드 시점에 사용된 유틸리티 클래스만 정적 CSS 파일로 최적화 생성하여 극도로 낮고 안정적인 로드 속도를 보장합니다.
    *   **신속하고 일관된 디자인 시스템**: 토큰 기반(`font-bold`, `rounded-lg`, `shadow-md`) 스타일 적용으로 UI의 시각적 통일성을 손쉽게 유지하며 반응형 웹(`md:`, `lg:`)을 완벽히 지원합니다.

### 4) Framer Motion (고감도 애니메이션 라이브러리)
*   **도입 배경 및 이유**:
    *   포트폴리오는 방문자(면접관, 인사 담당자)에게 첫 인상에서 압도적인 **'감동(WOW Factor)'**을 주어야 합니다. 
    *   CSS transition만으로는 구현이 어려운 마이크로 인터렉션(카드 마우스 오버 시 부유 효과, 자연스러운 모달 Fade-in/out, 제스처 등)을 물리 엔진 기반으로 부끄럽지 않은 고급 차원의 프리미엄 UI/UX로 구현하기 위해 채택했습니다.

### 5) Apache ECharts (`echarts-for-react`)
*   **도입 배경 및 이유 (Chart.js / Recharts 대비 장점)**:
    *   단순한 텍스트 리스트가 아닌 **레이더 차트(Radar Chart), 바 차트(Bar Chart) 등 직관적이고 미려한 스킬 시각화(`SkillCharts.tsx`)**를 위해 도입했습니다.
    *   Canvas 기반 렌더링으로 브라우저 부하가 매우 적고, 데이터 시각화의 자유도와 애니메이션 표현력이 대다수 JS 차트 라이브러리 중 최상급입니다.

### 6) Context API (`LanguageContext.tsx`) 기반 경량 다국어(i18n) 설계
*   **도입 배경 및 이유**:
    *   다국어(한국어/영어) 지원을 위해 무겁고 번들 용량을 차지하는 `i18next` 외부 라이브러리 대신, React 순정 라이트웨이트 솔루션인 **Context API**를 활용하여 직접 다국어 전환 구조를 구현했습니다. 외부 의존성을 낮추고, 단일 관심사로서 가볍고 쾌적하게 언어 상태 제어를 주입했습니다.

## 🖥️ 3. 백엔드(Backend) 기술 스택 및 도입 배경

### 1) Java 17 & Spring Boot 4.x (Enterprise Backend)
*   **도입 배경 및 이유**:
    *   **대용량 트래픽 및 확장에 대비한 안정적 엔터프라이즈 구조**: 포트폴리오를 웹 CMS로 견고하게 운영하고 실전 엔터프라이즈 환경에서 쓰이는 MVC 및 Service 레이어 패턴 역량을 과시하기 위해 선택했습니다.
    *   Java 17의 텍스트 블록, 불변 레코드(Record), 강화된 Null/NPE 방어 문법 등 최신 Java LTS 기능들을 비즈니스 및 DTO 모델에 적극 투입할 수 있습니다.

### 2) Spring Data JPA (Hibernate ORM)
*   **도입 배경 및 이유 (MyBatis / 순수 JDBC 대비 장점)**:
    *   **객체 중심 도메인 설계**: SQL 쿼리에 종속적인 프로그래밍에서 벗어나, Java 객체(`Entity`)와 RDBMS 테이블을 1:1 매핑함으로써 상속, 연관관계 등 객체지향의 이점을 그대로 살렸습니다.
    *   **생산성 및 유지보수**: 기본적인 CRUD 쿼리를 작성할 필요 없이 JPA Repository가 인터페이스 메서드 규칙만으로 완성도 높은 SQL을 자동 생성하며, 스키마 수정 시 유지보수 속도가 극단적으로 빨라집니다.

### 3) PostgreSQL Database
*   **도입 배경 및 이유 (MySQL / H2 / SQLite 대비 장점)**:
    *   단순 가벼운 파일 DB(SQLite, H2)는 운영(Production) 무대에서 고도의 다중 동시성 처리 및 강력한 제약 조건을 보장하지 못합니다.
    *   **PostgreSQL**은 전 세계 엔터프라이즈 레벨에서 최고로 인정받는 오픈소스 RDBMS로, ANSI SQL 표준을 엄밀하게 준수하며 향후 JSON/JSONB 형태의 고급 데이터 컬럼이나 검색 엔진 확장을 자유롭게 수용할 수 있는 고성능 데이터베이스이기 때문에 선정했습니다.

### 4) Local File Upload & Custom Storage Clean-up (`LocalFileUploader.java`)
*   **도입 배경 및 이유 (AWS S3 대비 물리 호환 스토리지를 구축한 이유)**:
    *   프로젝트 개발 단계 및 자체 온프레미스 서버 환경에서 외부 클라우드 과금과 유효성 불특정에 의존하지 않기 위해 **독립적인 서버 로컬 파일 스토리지 시스템**을 구현했습니다.
    *   단순 저장만 하는 것이 아니라, 수정/삭제 시 **저장공간 낭비(Orphan File / Ghost Blob)를 막는 물리 파일 삭제 로직(`deleteFile`)**까지 풀스크래치로 서비스화했습니다.

### [Part A] 🏗️ 아키텍처 및 전반적 기획 관련 Q&A

#### Q1. "단순 포트폴리오 사이트라면 GitHub Pages나 Vercel에 정적(Static) 파일만 올리는 게 비용과 속도 면에서 나을 텐데, 굳이 무겁게 Spring Boot 백엔드와 PostgreSQL 데이터베이스까지 풀스택으로 연계한 이유가 무엇인가요?"
*   **💡 핵심 의도 파악**: 오버 엔지니어링 여부를 점검하고, 왜 이 아키텍처를 선택했는지에 대한 엔지니어의 통찰력을 보는 질문입니다.
*   **🗣️ 모범 답변**:
    > "좋은 지적 감사드립니다. 만약 변경 없는 고정된 텍스트와 스토리지만 보유한 웹이라면 정적 Hosting이 정답입니다. 하지만 제 포트폴리오의 디자인 목표는 **'내가 성장할 때마다 코드 배포(Deploy)나 수용 없이 언제든 관리자 모드에서 실시간으로 역량과 작업물을 관리할 수 있는 동적인 CMS(Content Management System)'**를 구축하는 것이었습니다. 
    > 
    > 프론트엔드와 백엔드를 모두 설계하면서 **Multipart 이미지 핸들링, 데이터 영속성 처리, CORS 정책 극복, 예외 제어**와 같은 실전 통신 생태계를 제가 A부터 Z까지 독립적으로 설계하고 해결할 수 있는 풀스택 역량이 있다는 것을 라이브로 증명하기 위해 구조적으로 선택했습니다."

#### Q2. "계층화 아키텍처(Controller - Service - Repository - Domain)를 정확하게 나눴고, 왜 Entity와 DTO(Data Transfer Object)를 명확히 분리했나요?"
*   **🗣️ 모범 답변**:
    > "단일 책임 원칙(SRP)과 **안전한 통신 경계**를 지키기 위해서입니다. 
    > 첫째, `Entity`는 데이터베이스 테이블 스키마와 직접 직교하는 도메인 핵심 클래스입니다. 이를 클라이언트 통신용으로 직접 열어버리면 불특정한 변경에 노출되고 무인경우 민감 데이터까지 리턴될 수 있습니다. 
    > 둘째, 클라이언트가 실제 필요로 하는 API 스펙(예: multipart/form-data 또는 JSON 필드)과 DB 모델 스펙이 1:1로 늘 부합하진 않습니다.
    > 따라서 `ProjectRequestDto`와 같은 DTO를 파티셔닝하여 **오버패치(Over-fetching) 및 보안 누수**를 방지하고, DB 스키마 수정이 API 스펙 붕괴로 번지는 커플링(Coupling)을 방어했습니다."

### [Part B] 🎨 프론트엔드(React, Vite, CSS, TS) 심층 Q&A

#### Q3. "Vite가 빠르다고 하셨는데, Webpack을 사용하는 일반 CRA(Create React App)와 비교했을 때 근본적인 빌드 속도 개선 원리가 무엇인지 상세히 설명해 주실 수 있나요?"
*   **🗣️ 모범 답변**:
    > "두 도구의 근본적 차이는 **'개발 서버 시작 시 번들을 언제, 어떻게 구축하느냐'**의 원리에 있습니다.
    > 
    > Webpack(CRA)은 서버를 구동하기 앞서 의존성 트리의 모든 JS 모듈을 크롤링하여 **단일 혹은 몇 개의 무거운 번들로 통번들링(Bundling)을 먼저 완결**한 뒤에야 서버를 띄웁니다. 소스 수정(HMR) 시에도 번들의 재생성 과정이 수반됩니다.
    > 
    > 반면, **Vite**는 코드를 변하지 않는 '의존성(Dependencies)'과 번번이 수정되는 '소스 코드(Source code)'로 분리합니다. 의존성은 Go 기반 초고속 **esbuild**로 빠르게 프리 번들링하고, 소스 코드는 현대 브라우저가 제공하는 **네이티브 ES Module(ESM)** 메커니즘을 이용해 HTTP로 필요한 파일만 온디맨드(On-demand) 요청 시점에 쪼개어 전달합니다. 덕분에 아무리 규모가 커져도 HMR이 지연 없는 *즉각적인 프론트엔드 최적의 DX*를 유지합니다."

#### Q4. "i18next 같은 유명 다국어 라이브러리가 많은데 굳이 React의 내장 Context API(`LanguageContext`)를 활용하여 다국어를 직접 고안한 배경이 무엇이며, 리렌더링 최적화는 어떻게 고려하셨나요?"
*   **🗣️ 모범 답변**:
    > "외부 라이브러리 채택을 결정할 땐 **'라이브러리 번들 가중치 대비 실익'**을 항상 고려해야 합니다. 포트폴리오 성격상 다국어 사전 리소스 양이 거대하지 않기에, 약 40KB+ 가량을 차지하는 외부 i18n 라이브러리보다 **무겁지 않고 종속성이 없는 내장 Context API**로 단일화된 번역 상태 공급 로직을 구현하는 것이 최적이라 판단했습니다.
    > 
    > 리렌더링 측면에서는 언어가 바뀔 때 전역 UI의 언어가 전환되어야 하므로 탑다운 리렌더가 자연스럽지만, 불필요한 비용을 줄이기 위해 차트 컴포넌트(`SkillCharts`)나 고정형 카드 컨테이너 내의 순수 계산 로직에는 **React 메모이제이션(`useMemo`, `useCallback`, `React.memo`)**을 적절히 결합하여 UI 애니메이션 스터터링 없이 쾌적하게 렌더되도록 유도했습니다."

#### Q5. "Framer Motion 및 ECharts 같은 동적 UI/차트 라이브러리 사용 시 브라우저 프레임 저하나 메모리 부하 이슈를 겪거나, 어떻게 대처하셨나요?"
*   **🗣️ 모범 답변**:
    > "애니메이션에서 렌더 부하를 줄이기 위한 첫 번째 원칙으로, 렌더링 파이프라인에서 레이어 리플로우(Reflow/Layout)를 일으키는 `width`, `height`, `top` 같은 속성 변형을 배제하고 GPU 가속을 적극 받는 **`transform`, `opacity`, `scale` 기반으로만 Framer Motion 모듈 트래지션을 구성**했습니다.
    > 
    > 또한, ECharts는 Canvas를 사용하여 DOM 엘리먼트를 무정형으로 불리지 않고 픽셀 단일 프레임 렌더링을 돕도록 설계했습니다. 반응형 브라우저 리사이징 시 무한 리스트 디스패치가 없도록 디바운싱(Debounce) 개념을 내포하는 ECharts의 온디맨드 옵션 및 해제(`dispose`) 사이클을 유지하여 메모리 누수를 예방했습니다."

#### Q6. "프로젝트 게시글 수정/삭제 및 이미지 교체 시(`LocalFileUploader.java`), DB 상의 Path만 변경하지 않고 실제 스토리지의 물리적 파일까지 찾아 삭제하도록 로직을 구현한 결정적 이유는 무엇이며, 예기치 않은 에러나 결함을 어떻게 방어하나요?"
*   **🗣️ 모범 답변**:
    > "데이터베이스에서 이미지 경로만 제거하거나 대체해 버리고 물리적인 파일(Uploads 경로)을 계속 방치할 경우, 고아 파일(Orphan File/Ghost Object)이 스토리지 내에 계속 적재되어 디스크 누수(Disk Overflows & Cost Waste)라는 심각한 인프라 결함으로 이어집니다.
    > 
    > 따라서 `deleteProject()` 또는 수정 시 이미지 변경 트리거(`updateProject`)에 접근하면 기존 이미지 URI를 분석해 물리 디스크에서 우선 안전하게 찾아 지우는 `deleteFile()` 로직을 구현했습니다. 만약 파일이 물리적으로 외부 조작 등으로 사라져 `File Naming Not Found` 상태여도 DB 삭제 자체가 예외로 Roll-back되거나 멈추지 않도록, `exists()` 체크 로직 및 방어적 Catch-Logging 로직으로 감싸 트랜잭션 안전성을 철저히 확보했습니다."

#### Q7. "클라이언트가 Multipart 형태로 대용량 이미지를 업로드할 때 발생할 수 있는 보안적 위험(예: 대용량 DoS, 파일 이름 충돌 등)에 대한 방어 로직은 어떻게 구축되었나요?"
*   **🗣️ 모범 답변**:
    > "보안과 인프라 방해 요소를 세 가지 관점에서 차단했습니다.
    > 1. **파일명 중복 및 경로 침해 방지 (Path Traversal 방어)**: 사용자가 업로드한 원본 파일명(Original Filename)을 절대 그대로 스토리지에 유지하지 않습니다. **`UUID` (범용 고유 식별자)**나 밀리세컨드 타임스탬프 난수화 접두어를 조합해 새 이름을 정제(`sanitize`) 저장하므로 파일 인젝션이나 크로스 덮어쓰기 오류가 발생하지 않습니다.
    > 2. **용량 폭격 제어**: Spring Boot `application.yml` 설정 내에 `max-file-size`와 `max-request-size`를 10MB로 상한선 제재하여 악의적인 대용량 무한 요청으로 인한 Out-Of-Memory 나 Network Bandwidth 고갈을 원천 차단했습니다.
    > 3. **검증 레이어**: 백엔드 컨트롤러 레벨에서 DTO 유효성 검사(`Validation`)를 통해 파일 미전송 및 불량 텍스트 파라미터 유입을 차단합니다."

#### Q8. "JPA 연관 관계를 쓸 때 지연 로딩(LAZY Loading)과 즉시 로딩(EAGER Loading) 중 어떤 것을 선호하며, N+1 문제가 발생할 때 어떻게 대처하겠습니까?"
*   **🗣️ 모범 답변**:
    > "제 데이터 접근 계층 설계의 철칙은 **'모든 연관 관계는 기본적으로 `FetchType.LAZY`(지연 로딩)로 설정한다'** 입니다. 즉시 로딩(`EAGER`)은 조회 연관 고리가 늘어날수록 의도치 않은 대거 Outer Join 및 제비뽑기식 쿼리가 폭주하여 성능 저하의 주범이 됩니다.
    > 
    > 지연 로딩 상황에서 리스트를 불러올 때, 각 프로젝트 게시물마다 추가 연관 객체(예: 각 프로젝트의 Tag 목록이나 리뷰 댓글 등)를 1건씩 따로 호출하여 SQL 쿼리가 1+N번 실행되는 **N+1 문제**가 포착될 경우, 
    > JPA Repository 인터페이스에서 **`@Query("SELECT p FROM Project p JOIN FETCH p.tags")`**와 같이 **Fetch Join**을 작성하여 단 하나의 쿼리로 최적의 일괄 결합 로딩을 달성하거나, 필요시 **`@EntityGraph`** 또는 DTO 직접 투명 조회 프로모션을 통해 퍼포먼스 최적화를 달성하겠습니다."

#### Q9. "REST API 에러 상황(예: 존재하지 않는 게시글 삭제 요청, JSON 타입 오류 등)에서 클라이언트 쪽에 예외를 어떻게 반환하고 있습니까?"
*   **🗣️ 모범 답변**:
    > "내부 서버 에러(500)나 Spring 스택트레이스를 사용자 브라우저 쪽에 날 것 그대로 방출하는 것은 프론트엔드의 화면 파괴와 심각한 백엔드 아키텍처 보안 노출을 초래합니다.
    > 
    > 이를 방어하기 위해 **`exception` 패키지를 단독 모듈화하여 Global Controller Advice (`@RestControllerAdvice`) 및 커스텀 Exception** 체계를 구축했습니다. 존재하지 않는 ID로 조회를 요구할 땐 `EntityNotFoundException`을 표출시키고, 어드바이스가 이를 포착해 `404 Not Found` 혹은 `400 Bad Request` 등 직관적인 HTTP 상태 코드와 함께 규격화된 에러 JSON 응답(예: `message`, `status`, `timestamp` 구조)을 반환하게 합니다. 프론트엔드 Axios는 이 규격화된 구조를 읽고 알기 쉬운 안내 문구를 즉시 UI 모달/토스트로 보여줍니다."

#### Q10. "향후 로컬 스토리지가 아닌 대형 클라우드 서비스(AWS S3, CloudFront)로 이관하거나 트래픽이 많아진다면 이 설계를 어떻게 리팩토링하실 텐가요?"
*   **💡 핵심 의도 파악**: 객체지향적 확장성(DIP/OCP 원칙 준수 여부)을 평가하고 미래 대형 서비스 경험 및 인프라 통찰력을 묻는 훌륭한 질문입니다.
*   **🗣️ 모범 답변**:
    > "객체지향 디자인 패턴 중 **개방-폐쇄 원칙(OCP)**과 **의존성 역전 원칙(DIP)**의 위력이 빛나는 대목입니다.
    > 
    > 현재 로컬 업로더 로직(`LocalFileUploader`)은 특정 스토리지 클래스 하나만 보는 것이 아니라, 상위 인터페이스인 `FileStorageService`(예: `upload()`, `delete()`)와 같은 인터페이스를 바라보도록 리팩토링하거나 설계할 수 있습니다. 
    > 추후 AWS S3로 넘어가게 된다면, 비즈니스 로직(ProjectService)은 전혀 한 줄도 바꾸지 않고 단지 AWS SDK 기반의 `S3FileUploader` 구현체를 새로 정의한 뒤 Spring DI(의존성 주입) 주입 빈을 `@Primary` 또는 `@Qualifier`로 갈아끼우기만 하면 유유히 연동이 끝납니다. 
    > 추가로 트래픽 확대 시에는 조회 요청 폭주를 소각시키기 위해 Spring에 **Redis** 기반의 인메모리 캐시 또는 S3 앞단에 **AWS CloudFront(CDN)**를 배치하여 정적 에셋 로딩 타임을 밀리초 단위로 파도쳐서 깎아내는 리팩토링을 구사하겠습니다."
